# AI harness

How Tennis Beat is built: Claude Code implements, Denys owns product decisions, review and device testing.

## Tools
- **Claude Code** with project settings in `.claude/settings.json` (permission allowlist, hooks) and subagents in `.claude/agents/`.
- **Xcode MCP** (`xcrun mcpbridge`, project-scoped in `.mcp.json`) and **XcodeBuildMCP** for builds, simulators, UI automation and screenshots.
- **GitHub Spec Kit** for spec-driven development; tasks become GitHub Issues.
- **GitHub**: public repo, squash-only merging, a ruleset on `main` (PR only, green CI, no force push or deletion), secret scanning and push protection.
- **Figma** as a showcase only. The design was exported once into `docs/design/`, which is now the source of truth; agents do not call Figma tools because the Starter MCP limit is exhausted.
- **fastlane** for screenshots, metadata and TestFlight (added later).

## Task cycle and gates
1. `/speckit-specify` → Denys sets `Status: Approved` in `spec.md`. **Gate 1 (human).**
2. `/speckit-plan`, `/speckit-tasks`, `/speckit-analyze`; `scripts/gates/check-artifacts.sh` must pass.
3. Implementation in a dedicated worktree, tests first, with evidence that they failed before the code (see below); hooks format on edit and run engine tests before the agent stops.
4. Build and simulator run via XcodeBuildMCP, screenshots in the PR.
5. `reviewer` subagent in a fresh context → `Reviewed-SHA`. Each report is posted as a PR comment: verdict, SHA, numbered findings (R<review>-<n>) with severity and outcome. The reviewer also verifies the feature's `test-expectation-changes.md` and `test-first-evidence.md` (see below).
6. PR + CI. Evidence is valid only for the reviewed SHA. The PR body starts with `Reviewed-SHA: <full 40-character SHA>`; the **review-gate** CI job fails unless it equals the PR head SHA (see below).
7. Denys reviews and merges. **Gate 2 (human).**
8. Before TestFlight: device checklist below. **Gate 3 (human).**

## Test expectation changes
Rule (Denys, 2026-10-13). A test's expectation is the encoded rule. Changing it after the code exists can make a test agree with a bug.
- **Applies to:** any change to what a test asserts (expected value, expected error, or a positive control's condition) made after the code that the test checks was written. This includes code already on `main` and code written earlier in the same branch. Writing a new test before its code, renaming, or changing a point sequence while keeping every expected value is not an expectation change. Neither is a test-helper change that leaves every expectation as it was, such as how a UI test finds an element (e.g. the End confirmation button by its EN, PL or UK label) or how long it waits (Denys, #23 R1-2). If in doubt, list it.
- **Where:** a file in the diff, `specs/<feature>/test-expectation-changes.md`, for the feature whose tests changed. Not the PR body: the body is the implementer's summary, which the reviewer must not read.
- **Format:** one section per PR, newest last, headed with the branch name (and the PR number once known). One row per change: test name, old expectation → new expectation, and the source it agrees with: the ITF note ID (from `docs/rules/itf-notes.md`), or, for behavior no ITF rule covers, the spec requirement or scenario ID (e.g. `FR-012`, `US3-S4`) (Denys, #23 R1-1). `—` only for a non-rule property such as a stats identity, with a reason. A branch that changes test files but no expectation adds a section saying "none".
- **The reviewer** reads the file as part of the diff and checks it against the diff: every expectation change in the diff must be listed, and every listed change must agree with the cited entry in `docs/rules/itf-notes.md` or the cited requirement or scenario in the feature's `spec.md`. An unlisted change, or one that contradicts its note, is a blocker finding.

## Test-first evidence
Rule (Denys, 2026-10-15). A test that has never failed may not be able to fail. #24's tests were written before the code but first run after it, so nothing showed they could catch its absence.
- **Applies to:** every PR that adds tests (unit, UI or engine).
- **What:** for each added test, a run against the code *before* the implementation it checks, and the result: the failing test names with the failing assertion, or the compile errors when the test uses API that did not exist yet. Record the commit SHA of the code it ran against; if the tests were overlaid on an older commit, name both commits and the command. Commit the tests before the implementation so that commit is the evidence.
- **Tests of existing code** (coverage added for code already on the base, or an audit of an existing screen) have no "before". Record a run against a deliberate break of that code instead: the base SHA, the mutation as a short diff, and the failing test names. The mutation is never committed.
- **A test that did not fail** before the implementation or under its mutation is listed with that result and a reason; it is not dropped silently.
- **Where:** `specs/<feature>/test-first-evidence.md`, one section per PR, newest last, headed with the branch name (and the PR number once known). Not the PR body, which the reviewer must not read; the PR body may link the section.
- **The reviewer** checks the file against the diff: every test the diff adds is listed; each listed SHA exists in the branch history or on the base; at that SHA the code the test checks is absent (or the recorded mutation removes it); and the failures named are ones that test can produce. The reviewer may re-run a listed unit test to confirm. A missing entry, or evidence that does not match the diff, is a blocker finding.

## Review gate and merge order
Added after PR #7 was merged at a head no reviewer had passed: nothing on GitHub enforced `Reviewed-SHA`.
- **review-gate** (`.github/workflows/review-gate.yml`, script `scripts/gates/check-review-gate.sh`) runs on every PR, spec PRs included. It passes only when the PR body has exactly one line `Reviewed-SHA: <40-hex SHA>` and that SHA equals the PR head. It re-runs on pushes and on PR body edits. Use `Reviewed-SHA: pending` until a review passes; the check fails on it by design.
- Denys makes review-gate a required check in the "Protect main" ruleset.
- **Merge order** for every PR:
  1. Denys's approval commit comes first. For a spec PR this is the commit that sets `Status: Approved`; for any PR, Denys's requested changes are committed before the final review.
  - **Decisions are PR comments** (Denys, 2026-10-15, after #28's plan-review decisions had no recorded source): Denys records approvals and decisions as comments on the PR. The approval commit, whether Denys makes it or the agent makes it at his request, cites the comment's link in its message and in the spec's Status line, and every spec or plan text that applies a decision links to that comment. A decision given only in a chat session counts once it is in such a comment; the reviewer checks each decision against its comment.
  2. The agent runs the final review on that head and posts the report. Only if the verdict is PASS does it set `Reviewed-SHA` to the head; any blocker, major finding or Conflict is CHANGES_REQUESTED, and the line stays `pending` (Denys, 2026-10-14). Nothing is pushed after a PASS.
  3. Denys merges once review-gate and CI are green on that head. Any later push invalidates the review and the gate fails until a new review passes.
- **Spec PRs stay in Draft** (Denys, 2026-10-15, after #26 was merged with the spec still Draft): the agent opens every spec PR as a GitHub draft PR and keeps it in Draft until Denys's approval commit (`Status: Approved`) has passed the final review. Only then does the agent mark the PR ready for review, so a spec PR that can be merged always carries an approved, reviewed spec.

## Xcode project format
- The project was created with Xcode 27 but is saved in **Xcode 26.3 format** (`objectVersion = 100`), because the CI runner image (`macos-26`) only has Xcode 26.x.
- **In Xcode 27, do not re-enable strict project validation.** Also decline "Update to recommended settings" if it offers to. Either one writes the root key `validationLevel` into `project.pbxproj`, which forces format 110. Xcode 26 refuses to open that ("future Xcode project file format"), and every app build in CI fails.
- `scripts/gates/check-project-format.sh` runs in CI and fails on `objectVersion > 100` or on `validationLevel`. To fix it, delete the `validationLevel = 1;` line and set `objectVersion = 100;`.
- Revisit this once the runner image ships Xcode 27.

## Example: starting a feature
The first feature is the scoring engine:
```text
/speckit-specify Scoring engine in Packages/TennisCore. A match is an ordered list of Codable
events (point won by me/opponent, plus setup: format, first server). Match state is a pure
reduction of events. Formats: singles; 1 set or best of 3; set length 4, 6 or 8 games;
Advantage or No-Ad; tie-break at N–N; optional match tie-break to 10 instead of the deciding
set. The state exposes: point display per player, games and sets, server, serving side
(deuce/ad), tie-break flags, change-of-ends events, set and match winner. Undo removes the
last event and must work across game/set boundaries and after the match ends. Derived stats:
points won on serve and on return, service games held, break points converted and saved.
Every rule must reference docs/rules/itf-notes.md. No UI, HealthKit or persistence code.
```
Then Denys reviews the spec and sets `Status: Approved`. After that: `/speckit-plan` → `/speckit-tasks` → `/speckit-analyze` → `/speckit-implement`.

## Device checklist (Denys, before every TestFlight build)
- [ ] Full match on court: scoring, undo, change-of-ends haptics
- [ ] Health permission denied: scoring still works, no crashes
- [ ] Health onboarding (spec 003, device check 2): on a fresh install the onboarding shows before New match; Continue shows the system Health sheet and every answer leads to New match; after Not now the onboarding returns on the next launch; once the sheet has been answered it never returns; at the default text size Continue is visible without scrolling, the text scrolls with a finger and with the Digital Crown up to Not now above Continue; and VoiceOver reads the title, the three lines, Continue, then Not now; on a cold launch right after install the onboarding still appears (the app waits at most 1 s for HealthKit's answer and skips the onboarding for that launch if it is slower)
- [ ] Workout keeps the app on screen (spec 003, device check 1): with Health allowed, the app stays frontmost at every wrist raise for a whole match: during play, while paused (including a pause over 10 minutes), and on the summary until the workout is saved
- [ ] Workout in Health (spec 003, device check 4): the saved workout shows in Fitness and Health as Tennis, from the match start to the moment the summary opened (the winning point or the confirmed End), with paused intervals, a heart-rate graph and active energy, and counts toward the Activity rings. If heart rate or energy is missing, report it: a spec change to FR-003/FR-004 follows, no workaround
- [ ] One workout per match (spec 003, device checks 6, 7, 15): Undo from the summary, then finishing again, leaves exactly one workout; a match ended with 0 points leaves none; the summary left open for 10 minutes saves the workout and Undo disappears
- [ ] Health denied (spec 003, device check 8): a full match scores normally, there is no heart-rate row, the summary shows Duration only, and Health has no workout
- [ ] Another workout running (spec 003, device check 10): start a match while the system Workout app has a workout running; the match starts; record which workout survives
- [ ] Workout battery (spec 003, device check 12): a 90-minute match with a workout uses about as much battery as the system Workout app's tennis workout (record the percentage)
- [ ] Workout without the iPhone (spec 003, device check 13): the workout saves on the watch and appears on the iPhone after they reconnect
- [ ] App ended mid-match with a workout running (spec 003, device check 14): after a force-quit, the relaunch saves the workout as it is and opens New match
- [ ] Always On: score readable, no seconds or animations
- [ ] Largest agreed Dynamic Type size (spec 002, Q9: every size on setup, controls and summary; the largest standard size on the score screen): nothing clipped. Layout is checked on the 40 mm watch simulator (the smallest watch watchOS 26 supports); the real-device check runs on Denys's own watch
- [ ] iPhone far away during the match: match arrives later
- [ ] Wet fingers / towel: no accidental points
- [ ] App killed mid-match: match restored with the same score
- [ ] Oldest supported watch, app killed during a 500-point match and relaunched: the restored score shows without a loading indicator (spec 001, SC-004)
